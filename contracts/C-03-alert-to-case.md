# C-03 — Alert 기반 Case 생성·연결

> **C-03 란** 경보(Alert)를 사건(Case)으로 넘기는 약속이다.
> 번호 체계는 [계약 지도](README.md#번호가-무슨-뜻인가) 참고.

- **방향** P2 `risk` → P3 `investigation`
- **방식** Spring Modulith 내부 비동기 이벤트
- **검증** T-03(Case 생성 기준) · T-04(AI 자동·수동) · T-05(동시성)
- **상태** **채택**

---

## 1. 이벤트 데이터

| 필드 | 뜻 |
|---|---|
| `alertId` · `tenantId` | 저장된 경보 ID 와 고객사 |
| `subjectType` / `subjectExternalId` | 조사 대상의 종류와 원천 ID |
| `riskLevel` | `LOW` / `MEDIUM` / `HIGH` |
| `ruleCode` / `ruleRevisionId` | 탐지 규칙과 그 버전 |
| `occurredAt` | **경보가 일어난 시각** (도착 시각이 아니다) |
| `evidenceEventIds` | 탐지 근거가 된 이벤트 ID 목록 |

## 2. 즉시 반환값은 없다

P2 와 P3 은 **같은 Spring Boot 안**에서 이벤트를 주고받는다.
내부 이벤트에 HTTP 201·202 를 쓰지 않는다.

예전 설계의 즉시 반환 필드 `caseId` / `linked` / `autoAiRequested` 는 **빠졌다.**
이벤트를 발행한 직후에는 `caseId` 를 알 수 없다.

## 3. Case 를 만드는 기준 — 채택

| 들어온 경보 | 결과 |
|---|---|
| **HIGH 1 건** | Case 생성·연결 + **최초 AI Job 자동 저장** |
| 같은 고객사·대상에서 **서로 다른 논리 규칙**의 MEDIUM 이상 2 건이 **30 분 이내** | Case 생성·연결만. **AI 는 자동 시작하지 않는다** |
| LOW, 단독 MEDIUM, **같은 논리 규칙**의 중복 경보 | Case 를 만들지 않는다 |

30 분은 **`occurredAt`(일어난 시각)** 기준이다. P3 에 도착한 순서가 뒤바뀌어도
판정이 흔들리면 안 된다(T-05).

## 4. 처리 규칙

- P2 가 Alert 를 저장하고 내부 이벤트를 발행한다. P3 은 **별도 처리**에서
  Case 생성 또는 기존 사건 연결을 판단한다.
- 같은 Alert 의 재전달·동시 처리·순서 차이가 있어도 **Case · Alert 연결 ·
  최초 AI Job 이 중복 생성되지 않는다.**
- Case 생성 · Alert 연결 · 최초 AI Job 저장은 필요하면 **하나의 트랜잭션**으로
  함께 커밋한다. FastAPI 원격 호출은 **그 뒤에** 따로 한다.
- **(추천안)** 이 비동기 경로에도 Registry 의 리스너별 처리 기록을 적용해,
  실패 시 같은 Alert 를 재처리할 수 있게 한다. 중복은 DB 제약과 업무 조건으로 막는다.

## 5. 결과를 확인하는 방법

P3 처리가 끝난 뒤 기존 Alert·Case 조회 경로에서 연결된 `caseId` 와 사건 정보,
최초 자동 AI Job 생성 여부를 확인한다.

**사건이 연결되지 않았다는 사실만으로 '처리 중'이라고 단정하지 않는다.**
LOW·단독 MEDIUM 은 정책상 Case 가 없는 것이 정상이다.

- **(추천안)** `SEC-01`(보안 직원 경보 화면)에서 HIGH 경보 상세는 Case 연결 여부를
  5 초 간격으로 최대 1 분 조회하고, 그 뒤에는 '다시 조회' 버튼을 준다.
- **(추천안)** MVP 1 에서는 Case 생성 전용 `PENDING` 상태·테이블을 **추가하지 않는다.**
