# 공통 필드 — 이름과 타입

> **D-3 이란** 개발 전에 사람이 정해야 했던 세 번째 결정이다(Decision).
> 일곱 개 계약 전부가 같은 필드를 주고받으므로, 이름과 타입을 먼저 맞춰 둔다.
> **상태: 확정 (2026-10-16)**

맞추지 않으면 3주차 통합에서 깨진다. 같은 뜻인데 한쪽은 `amount`, 한쪽은 `price`,
한쪽은 `Long`, 한쪽은 `BigDecimal` 이면 이벤트가 그대로 역직렬화되지 않는다.

---

## 1. 모든 이벤트·요청에 들어가는 필드

| 필드 | 타입 | 뜻 | 주의 |
|---|---|---|---|
| `eventId` | `String` | 이벤트 하나를 가리키는 전역 유일 ID. UUID 문자열 36자 | **CakeShop 이 만든다.** 플랫폼의 중복 판정 기준이다 |
| `tenantId` | `String` | 어느 고객사(쇼핑몰) 것인지 | **요청 본문의 값을 믿지 않는다.** 인증 정보에서 도출한다 |
| `occurredAt` | `Instant` | 그 일이 **실제로 일어난** 시각. UTC 로 저장 | 받은 시각이 아니다. 화면에서만 KST 로 바꾼다 |
| `schemaVersion` | `int` | 이벤트 모양의 버전. `1` 부터 | 필드를 늘리면 올린다 |

`occurredAt` 과 "받은 시각"을 섞지 않는 이유는 `risk`(P2) 의 규칙이 **일어난 순서**로
판단하기 때문이다. 재시도로 늦게 도착한 이벤트가 나중 일로 취급되면 탐지가 틀어진다.

---

## 2. 금액 — `long`, 원 단위 정수

```java
long expectedAmount;   // 125000  = 125,000원
```

| 쓰지 않는 것 | 이유 |
|---|---|
| `BigDecimal` | 원화에는 소수점이 없다. 쓰는 순간 `compareTo` · 스케일 비교가 따라붙는다 |
| `int` | 최대 약 21억이다. 금액 **합계**가 넘을 수 있다 |
| `double` | 0.1 을 정확히 담지 못한다. 돈에 쓰지 않는다 |
| `Long` (박싱) | `null` 이 들어온다. 금액이 없으면 `0` 이다 |

**금액은 `null` 이 아니다.** 없으면 `0` 이다.

### 2.1 이름은 `price` 가 아니라 `...Amount` 다

`price` 는 **단가** — 상품 하나의 값이다. 그건 CakeShop 상품 테이블 안에만 있고,
플랫폼으로 넘어오지 않는다. 플랫폼이 다루는 것은 전부 **금액**(amount) 이다.

그리고 금액은 한 종류가 아니다. `amount` 한 단어로 두면 **어느 금액인지 알 수 없다.**
그래서 **앞에 무슨 금액인지 붙인다.**

| 뜻 | 이름 | 나오는 곳 |
|---|---|---|
| 주문 금액 | `orderAmount` | C-01 주문 생성 |
| 결제된 금액 | `paidAmount` | C-01 결제 확정 |
| 취소·환불 금액 | `refundAmount` | C-01 취소 확정 |
| 예상 순정산액 | `expectedAmount` | C-07 — **이미 코드에 있다** |
| 시작 자금 | `openingBalance` | `cashflow` (P6) |
| 예정 지출 | `scheduledAmount` | `cashflow` (P6) |
| 날짜별 예상 잔액 | `projectedBalance` | `cashflow` (P6) |
| 상품 단가 | `price` | **CakeShop 안에만** |

> 잔액은 `...Balance`, 그 밖의 금액은 `...Amount` 다.

## 3. 시각과 날짜

| 뜻 | 타입 | 이름 | 예 |
|---|---|---|---|
| 시각(시·분·초까지) | `Instant` | `...At` | `occurredAt`, `createdAt`, `detectedAt` |
| 날짜만 | `LocalDate` | `...Date` | `expectedDate`, `fromDate`, `toDate` |

`LocalDateTime` 은 쓰지 않는다. 시간대 정보가 없어 UTC 인지 KST 인지 코드만 봐서는
알 수 없다. **DB 에는 UTC 로 넣고, 화면에서만 KST 로 바꾼다.**

---

## 4. ID

| 어디서 온 ID | 타입 | 예 |
|---|---|---|
| 외부(CakeShop)에서 온 것 | `String` | `subjectExternalId`, `eventId`, `settlementId` |
| 플랫폼이 만든 PK | `Long` | 엔티티 `id` |

CakeShop 의 `orders.id` 는 숫자지만, **플랫폼에서는 문자열로 받는다.**
고객사가 늘어나면 ID 체계가 숫자가 아닐 수 있고, 플랫폼 PK 와 섞일 위험도 없앤다.

---

## 5. 열거형(enum)은 문자열로 보낸다

`eventType` · `status` 같은 값은 **이름 문자열**로 주고받는다. 순서 번호(ordinal)를
쓰면 나중에 값을 중간에 끼워 넣는 순간 과거 데이터의 뜻이 바뀐다.

```
"LOGIN_FAILED"   O
2                X
```

모르는 값이 오면 **버리지 않고 저장한 뒤 경고를 남긴다.** 보내는 쪽이 먼저
배포되는 경우가 있다.
