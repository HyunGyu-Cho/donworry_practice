# 탐지 규칙 설계 방침

> 위험 규칙(`risk` 모듈 · P2)을 만들 때의 공통 틀이다. **숫자는 여기서 정하지 않는다.**
> 1주차에 실제 데이터를 보고 정한다. 정하는 **방법**과 **틀**만 적는다.
>
> 조사 일자 2026-10-16. 근거는 마지막 절에 모아 뒀다.

---

## 1. 규칙은 빈칸 4개짜리 문장이다

실제 보안 제품의 규칙을 열어 보니 전부 같은 모양이었다.

```
[무엇]을 묶어서 / [얼마] 동안 / [몇 번] 넘으면 경보. 단 [이것]은 빼고.
```

| 빈칸 | 이름 | 없으면 |
|---|---|---|
| 무엇을 묶어서 | 묶음 키 | 전체가 한 덩어리가 돼 탐지가 안 된다 |
| 얼마 동안 | 시간 구간 | 경계에서 새거나 같은 일로 경보가 여러 번 난다 |
| 몇 번 | 임계값 | 오탐이 폭증한다 |
| 무엇은 빼고 | 제외 목록 | 운영 노이즈가 경보로 올라온다 |

**제외 목록을 가볍게 보지 않는다.** 참고한 제품의 규칙은 조건의 절반이 제외였다 —
내부 IP, 시스템 계정, 머신 계정, 그리고 "설정 오류로 흔히 뜨는 실패 코드" 5개를 뺀다.
그 제품은 이 규칙의 노이즈를 스스로 **High** 로 표기하고, 오탐 사유를 넷 적어 두었다
(자동화·스케줄 작업 실패, 인증 설정 오류, 서비스 계정 비밀번호 만료, 인프라 장애).

## 2. 시간 구간은 '고정 구간'으로 자른다

흘러가는 창(sliding window)이 아니라 **잘라 놓은 칸**(1분 칸, 5분 칸)에 넣고 센다.
구현이 단순하고 같은 일로 경보가 두 번 나지 않는다.

> **주의 — 구간은 이름보다 길다.** 참고한 결제 서비스는 `hourly` 를
> **최대 3,900초(1시간 5분)** 로, `daily` 를 **최대 90,000초(25시간)** 로 계산한다.
> 5분 칸을 쓰기 때문에 한 칸이 더 붙는다.
>
> **그래서 `C-03`(경보를 사건으로 넘기는 약속)의 "30분 이내"도 구현하면 30분이 아니다.**
> 칸 크기를 정하고 문서에 적어야 `T-05`(도착 순서가 바뀌어도 30분 정책이 왜곡되지
> 않는다)의 합격선이 생긴다.

## 3. "로그인 실패 반복"은 한 규칙이 아니라 둘이다

세는 기준이 **반대**인 두 공격이 같은 이름에 묶여 있었다.

| | 한 계정을 집중 공략 | 여러 계정을 한 번씩 |
|---|---|---|
| 하는 짓 | 비밀번호를 추측한다 | **다른 데서 유출된 목록**이 여기서도 통하는지 본다 |
| 모양 | 계정 1개에 실패 다수 | 계정 다수에 실패 1~2회 |
| **묶음 키** | **계정** | **IP** |
| 표준 분류 | OWASP OAT-007 | OWASP OAT-008 |

**계정 기준으로만 규칙을 만들면 두 번째는 잡히지 않는다.** 계정마다 한 번씩만
실패했으므로 어느 임계값에도 걸리지 않는다.

그리고 두 번째를 잡으려면 **실패 횟수만으로는 부족하다.** 참고한 제품은
**"서로 다른 계정 수 ≥ 2"** 를 조건에 같이 넣는다. 이것이 "비밀번호를 잊은 한 사람"과
공격을 가르는 지점이다.

## 4. 실패 뒤에 성공이 오면 임계값이 훨씬 낮다

실패만 쌓이는 것은 "안 열렸다"다. 실패 뒤 성공은 **"열렸다"**다.
참고한 제품은 같은 현상에 임계값을 20배 다르게 둔다.

| 규칙 | 임계값 | 등급 |
|---|---|---|
| 실패만 (IP 기준, 1분 칸) | **100건** + 서로 다른 계정 2개 이상 | medium |
| **실패 k회 → 성공** (계정+IP, 짧은 구간) | **5건** | medium (risk 47) |

우리 등급 체계로는 **"실패 뒤 성공"을 HIGH 로 두는 것이 맞다.** `C-03` 정책상
HIGH 1건이면 사건(Case)이 생기고 AI 조사가 자동 시작된다.

## 5. 우리 규칙 후보

0-B 조사 결과 확보 가능한 신호는 **로그인 성공·실패**(CakeShop 에 추가 구현),
**주문 생성 · 결제 확정 · 취소/환불 확정 · 회원 정지/해제** 다. 그 범위 안에서만 만든다.

| ruleCode | 묶음 키 | 구간 | 조건 | 등급 |
|---|---|---|---|---|
| `LOGIN_FAIL_BURST_PER_ACCOUNT` | 계정 | 5분 | 실패 ≥ N | MEDIUM |
| `LOGIN_FAIL_SPRAY_PER_IP` | IP | 1분 | 실패 ≥ N **AND 서로 다른 계정 ≥ 2** | HIGH |
| `LOGIN_FAIL_THEN_SUCCESS` | 계정 + IP | 짧은 순서 구간 | 실패 k회 → 성공 | **HIGH** |
| `LOGIN_NEW_IP_RANGE` | 계정 | — | 직전 성공과 다른 IP 대역 | MEDIUM |
| `ORDER_VELOCITY_PER_MEMBER` | 회원 | 1시간 | 주문 수 > N | MEDIUM |
| `REFUND_VELOCITY_PER_MEMBER` | 회원 | 1일 | 취소·환불 확정 수 > N | MEDIUM |

> 지역 판정은 하지 않는다. IP 를 지역으로 바꾸려면 별도 데이터베이스가 필요해
> 4주 범위에서 뺐다(`C-01` 3.6절). 규칙도 **IP 대역 수준**으로 만든다.

## 6. 값이 없는 필드는 `!=` 로도 걸리지 않는다

참고한 결제 서비스 문서의 한 줄이다.

> 없는 값과 어떤 값을 비교하면(`=`, `!=`, `>`, `<` 무엇이든) **항상 거짓**이다.

**지금 열려 있는 "로그인 실패 시 식별자" 문제와 정면으로 만난다.**
없는 계정으로 로그인 실패하면 회원 ID 가 비어 있다. 그 상태에서
`subjectExternalId != null` 같은 조건을 쓰면 **아무 경보도 안 나고 조용히 실패한다.**

그 서비스는 이것 때문에 `is_missing()` 함수를 따로 뒀다.
우리도 **"값 없음"을 1급 상태로 다룬다** — `C-07`(예상 정산 유입 조회)에서
`resultStatus` 로 "자료 없음"과 "조회 실패"를 가른 것과 같은 원칙이다.

각 규칙은 식별자가 없을 때의 동작을 **명시한다** — 규칙을 건너뛸지,
"미상" 주체로 셀지.

## 7. 한 이벤트가 여러 규칙에 걸릴 때

참고한 두 결제 서비스 모두 **동작 종류로 우선순위를 두고, 맞으면 거기서 멈춘다.**
한쪽은 `3DS 요청 → 허용 → 차단 → 검토` 순이고, 같은 종류끼리는 순서가 없다.

우리는 차단을 하지 않으므로 그대로 쓸 수는 없다. 다만 **경보를 몇 개 만들지**는
정해야 한다. 기본값은 **"걸린 규칙마다 경보 1건"** 이고, `C-03` 이 사건 쪽에서
중복을 흡수한다(같은 논리 규칙의 중복 경보는 사건을 만들지 않는다).

## 8. 거래 쪽 특징값은 세 기간을 함께 본다

참고 교재가 쓰는 집계 피처는 고객별로 둘이고, **기간을 1일 · 7일 · 30일 셋**으로 둔다.

```
회원의 n일간 거래 건수
회원의 n일간 평균 금액
n = 1, 7, 30
```

**기간을 하나만 두면 이 둘을 구분할 수 없다.**

| | 30일 기준 | 1일 기준 |
|---|---|---|
| 원래 많이 사는 사람 | 많다 | 평소만큼 |
| **갑자기 많이 사는 사람** | 적다 | **폭증** |

## 9. '탐지가 늦는 것'과 '정답지가 늦게 나오는 것'은 다르다

섞어 쓰기 쉬운 두 시각이다.

| | 언제 | 고객사 화면에 영향 |
|---|---|---|
| **경보·사건이 뜨는 시각** | **즉시** (초~분) | **없다. 기다리지 않는다** |
| **"그게 진짜였다"는 판정 기록** | 사람이 확인한 뒤 | 없다. 고객사가 보는 화면이 아니다 |

참고한 교재가 가맹점 위험도 계산 구간을 **7일 뒤로 밀어 두는 것**은 **아래쪽** 때문이다.
교재가 이유를 직접 밝힌다 — 사기 거래는 *"조사가 끝나거나 고객이 이의를 제기한
뒤에야 발견된다"*. 카드 사기는 탐지가 느린 것이 아니라 **정답지가 늦게 나온다.**

참고로 Elastic 규칙은 **5분마다 돌며 최근 9분을 본다.** 분 단위다.
교재의 7일과 Elastic 의 9분은 **서로 다른 것을 재는 숫자**다.

### 지금 우리 규칙에는 해당 사항이 없다

5절의 규칙 후보 여섯 개는 전부 **"지금 벌어지는 일"** 만 본다 — 로그인 실패 횟수,
실패 뒤 성공, 다른 IP 대역, 주문 건수, 환불 건수. **과거 판정 기록을 재료로 쓰는
규칙이 하나도 없다.**

걸리는 것은 이런 규칙을 **추가할 때**다.

> "이 회원은 **예전에 사기 판정을 받았으니** 위험도 +N"

그런 규칙을 만들면 **판정이 끝난 사건만** 재료로 쓰고, 계산 구간을 판정 지연만큼
뒤로 밀어야 한다. 그러지 않으면 아직 직원이 보지도 않은 사건을 근거로 쓰게 되고,
**시험에서는 맞고 실제로는 맞지 않는** 코드가 된다.

**4주 범위에는 그런 규칙이 없다.** 추가할 때 이 절을 다시 본다.

## 10. 잘 되는지는 '상위 몇 건'으로 잰다

경보가 많으면 사람이 다 못 본다. 산수로 확인할 수 있다.
Microsoft 제품 문서는 경보 하나에 **최대 30분**의 수동 확인이 필요할 수 있다고 적는다.

| 하루 건수 | 건당 30분이면 | 건당 5분이면 |
|---|---|---|
| 500건 | 250시간 — 한 사람이 **31일** | 41시간 — 5명이 하루 종일 |
| 100건 | 50시간 — 한 사람이 6일 | 8시간 — 한 사람이 하루 |
| 16건 | 8시간 — 한 사람이 하루 | 1.3시간 |

그래서 **전체 정확도는 쓸모가 없다.** 99% 여도 하루 500건이면 밀리고, 밀리면 안 본다.

| 재는 법 | |
|---|---|
| 전체 정확도 | ❌ 양을 고려하지 않는다 |
| **상위 k건 정확도** | ✅ 하루 k건만 본다고 보고, **그 k건 중 몇 건이 진짜였나** |

업계에서는 이 k 를 **조사 예산**(alert budget)이라 부르고 전체의 0.1~5% 범위로 둔다.

### 우리 구조에서 세어야 하는 것은 '사건' 이다

우리는 사람이 경보를 하나하나 보지 않는다. **사건(Case)을 본다.**

```
경보 많이 ──→ [C-03 정책] ──→ 사건 적게 ──→ 사람이 본다
```

`C-03`(경보를 사건으로 넘기는 약속)의 정책이 곧 **사람에게 올라가는 양을 줄이는
장치**다. 사람에게 올리지 않는 조건이 이미 셋이다.

| 들어온 경보 | 사건이 되나 |
|---|---|
| LOW | 안 된다 |
| 단독 MEDIUM | 안 된다 |
| 같은 논리 규칙의 중복 경보 | 안 된다 |
| HIGH 1건 | 된다 (+ AI 조사 자동 시작) |
| 서로 다른 규칙의 MEDIUM 이상 2건이 30분 내 | 된다 |

→ 따라서 정해야 하는 숫자는 **`하루 경보 k건`이 아니라 `하루 사건 k건`** 이다.
P2 · P3 가 정하고, `T-03`(Case 생성 기준) 검증에 넣는다.

경보 수는 그 다음 문제다 — **경보 500건이 사건 몇 건이 되는지**가 규칙 임계값을
정하는 기준이 된다.

## 11. 아직 정하지 않은 것

칸 크기 · 임계값 N·k · 제외 목록 · 식별자가 없을 때의 동작 · 하루 사건 상한은
**[docs/ROADMAP.md](../docs/ROADMAP.md) 한 곳**에 모아 두었다. 여기에 다시 적지 않는다.
정해지면 그 줄을 지우고 이 문서의 해당 절에 **정해진 값**을 적는다.

## 12. 범위 밖 — 결제 승인 전 차단

검토 과정에서 이런 흐름이 제안되었다.

```
주문 검증 → 기존 승인 확인 → 플랫폼의 위험평가 → 허용 시 결제 최종 승인
```

**채택하지 않는다.** 세 곳과 충돌한다.

| | |
|---|---|
| 기획서 | 이 기능은 **MVP 2** 이고 "이번 4주 필수 범위 아님" |
| `T-14` | "플랫폼 장애가 CakeShop 의 결제를 막지 않는다" — 정반대가 된다 |
| `D-2` 결정 | 기록과 전송을 분리했는데 이 흐름은 다시 묶는다 |

우리가 만드는 것은 **결제가 끝난 뒤 수상한지 보는 장치**다. 결제를 막는 장치가 아니다.

## 13. 결제 이벤트는 '승인' 뒤에 보낸다

결제는 두 단계로 나뉜다.

| 단계 | 상태 |
|---|---|
| 본인 확인(인증) | 카드 주인인지 확인됨. **아직 돈은 빠지지 않았다** |
| **승인** | 실제로 금액이 차감된다 |

**본인 확인 시점에 이벤트를 보내면 돈이 빠지지 않은 결제를 예상 정산에 넣게 된다.**
`T-09`(확정된 금액만 차감)가 깨진다.

`C-01` 1.1절이 훅 지점으로 `PaymentService.completePayment` 를 고른 것은
**이 기준에 맞는다** — 재고 차감·주문 상태 변경과 한 트랜잭션이고, 승인 응답 이후다.

> 결제사 연동은 전부 CakeShop 안에서 끝난다. 플랫폼은 결제사를 호출하지 않는다.
> 승인 전 금액 검증(주문번호로 미리 저장한 금액과 비교)도 CakeShop 의 책임이다.
