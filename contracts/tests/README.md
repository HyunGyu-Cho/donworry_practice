# T-01 ~ T-15 — 검증 항목

> **T-xx 란** 무엇이 통과해야 완성인지 정한 **합격 기준**(Test)이다.
> 번호 체계는 [계약 지도](../README.md#번호가-무슨-뜻인가) 참고.

**항목을 적은 것과 통과한 것은 다르다.** 실제 실행 결과가 있어야 검증 완료다.
각 항목은 **실행 조건**과 **기대 결과**로 나뉜다.

| 분류 | 항목 |
|---|---|
| 보안 업무 | T-01 ~ T-08 |
| 정산·현금흐름 | T-09 ~ T-12 |
| 화면·배포 회귀 | T-13 ~ T-15 |

## 테스트 종류

| 종류 | 대상 |
|---|---|
| **단위** | 위험등급 규칙, 30 분 조건, 예상 정산·현금흐름 계산처럼 입력에 따라 결과가 정해지는 로직 |
| **통합** | 실제 DB 의 FK·UNIQUE·트랜잭션, 중복 요청, 동시성, 모듈 간 데이터 계약 |
| **API 계약** | HTTP 요청·응답 상태·필드·권한·오류 처리, 내부 Java API 반환값 |
| **장애 복구** | P2 소비 실패, FastAPI 중단, 콜백 누락, 정산 조회 실패 |
| **최종 시연** | CakeShop 이벤트 → 직원 판정 → 고객사 조치, 그리고 독립 자금관리까지 화면에서 |

# 보안 업무

## T-01. 이벤트 중복 접수 — P1

**실행**
1. 같은 CakeShop 이벤트를 두 번 전송한다.
2. 같은 ID 인데 **내용이 다른** 이벤트도 전송한다.

**기대 결과**
- 같은 원본은 플랫폼에 **한 번만** 기록된다.
- 중복 수신은 기존 이벤트를 재사용한다.
- 같은 ID 에 다른 내용은 **충돌로 거절**하고 기존 데이터를 덮어쓰지 않는다.

관련 계약: [C-01](../C-01-cakeshop-event.md) · [C-02](../C-02-event-distribution.md)

## T-02. P2 와 P5 의 업무 독립성 — P1 · P2 · P5

**실행**
1. P2 와 P5 가 **모두** 쓰는 결제 이벤트를 수신한다.
2. **P2 처리만 의도적으로 실패**시키고 P5 처리 완료를 확인한다.
3. 서버를 재시작하거나 복구 절차로 P2 의 미완료 이벤트를 재처리한다.
4. 같은 이벤트를 다시 전달해 P5 의 중복 반영 여부를 확인한다.

**기대 결과**
- Registry 에서 **리스너별** 처리 결과를 구분해 확인할 수 있다.
- P5 정산 처리가 정상 완료되고, **P2 의 실패 때문에 되돌려지지 않는다.**
- P2 처리만 재시도 대상이 되고 복구 후 정상 처리된다.
- 성공한 P5 결과는 재전송·재시도 후에도 **중복 반영되지 않는다.**

관련 계약: [C-02](../C-02-event-distribution.md)

## T-03. Case 생성 기준 — P2 · P3

**실행**
1. LOW 경보 1 건과 MEDIUM 경보 1 건을 각각 발생시킨다.
2. 같은 고객사·대상에 **서로 다른** MEDIUM 이상 규칙 2 건을 30 분 이내 발생시킨다.
3. **같은 규칙**으로 생성된 중복 경보 2 건을 발생시킨다.
4. 두 MEDIUM 경보를 **30 분 초과** 간격으로 발생시킨다.
5. HIGH 경보 1 건을 발생시킨다.
6. Alert 저장 직후와 비동기 Case 처리 완료 후의 조회 결과를 **구분해** 확인한다.

**기대 결과**
- LOW 1 건 · MEDIUM 1 건 · 같은 규칙 중복 · 30 분 초과 조합은 Case 를 만들지 않는다.
- 서로 다른 MEDIUM 이상 규칙 2 건이 30 분 이내면 Case 가 생성·연결된다.
- HIGH 1 건이면 Case 가 생성·연결된다.
- P2 의 이벤트 발행 직후 `caseId` 반환을 요구하지 않는다.
- Case 가 없는 LOW·단독 MEDIUM 을 **"생성 중"으로 표시하지 않는다.**
- **서로 다른 고객사의 같은 회원 ID 는 같은 Case 로 합쳐지지 않는다.**

관련 계약: [C-03](../C-03-alert-to-case.md)

## T-04. AI 자동 시작과 수동 시작 — P3 · P4

**실행**
1. HIGH 근거로 Case 를 생성한다.
2. MEDIUM 조합만으로 Case 를 생성한다.
3. 두 번째 Case 에서 직원이 **수동** AI 조사를 요청한다.

**기대 결과**
- HIGH Case 는 **직원 버튼 없이** 최초 AI Job 이 저장되고 실행된다.
- MEDIUM 조합 Case 에서는 자동 Job 이 생기지 않는다.
- 직원의 수동 요청에만 별도 Job 이 생성된다.
- **Job 접수와 보고서 생성 완료가 화면에서 별도 상태로** 표시된다.

관련 계약: [C-03](../C-03-alert-to-case.md) · [C-04](../C-04-ai-job-intake.md)

## T-05. Case 생성 동시성 — P2 · P3

**실행**
1. 같은 고객사·대상의 관련 Alert 를 **동시에** 여러 건 전달한다.
2. 같은 Alert 전달을 중복 실행한다.
3. 30 분 조건에 해당하는 Alert 가 **발생 시각과 다른 순서로** 도착하게 한다.
4. Case 저장 중 오류를 낸 뒤 같은 Alert 처리를 재실행한다.

**기대 결과**
- 정책상 같은 사건이면 Case 가 불필요하게 중복 생성되지 않는다.
- 같은 Alert 가 여러 Case 에 연결되지 않는다.
- **실제 발생 시각 기준의 30 분 정책이 도착·처리 순서 때문에 왜곡되지 않는다.**
- Case 생성 · 경보 연결 · 자동 AI Job 저장 중 **일부만 성공한 상태가 남지 않는다.**
- 재처리해도 불필요한 Case 나 최초 자동 AI Job 이 중복 생성되지 않는다.

관련 계약: [C-03](../C-03-alert-to-case.md)

## T-06. AI 중복·장애 복구 — P3 · P4

**실행**
1. 같은 `jobId` 를 여러 번 요청한다.
2. FastAPI 를 작업 중 중단했다가 재시작한다.
3. 완료 콜백을 **중복·역순으로** 전송한다.
4. 보고서 저장 전에 오류를 발생시킨다.

**기대 결과**
- 같은 최초 자동 AI Job 을 중복 생성하지 않는다.
- 미완료 Job 이 사라지지 않고 상태 확인·재처리가 가능하다.
- **과거 상태가 완료 상태를 되돌리지 않는다.**
- 저장되지 않은 보고서를 성공으로 표시하지 않는다.
- **실제 LLM 호출·과금까지 "정확히 한 번"을 보장한다고 주장하지 않는다.**

관련 계약: [C-04](../C-04-ai-job-intake.md) · [C-05](../C-05-ai-status-callback.md)

## T-07. 고객사별 접근 및 증거 격리 — P1 · P2 · P3 · P4

**실행**
1. 고객사 A 권한으로 B 의 Alert · Case · AI 증거를 조회한다.
2. A 의 Case 에 B 의 경보·보고서 근거를 연결하려 한다.
3. 다른 역할로 직원 전용 판정 API 를 호출한다.

**기대 결과**
- 조회·연결·판정 요청이 **차단된다.**
- **DB 와 애플리케이션 권한 양쪽에서** 다른 고객사 참조가 막힌다.
- AI 보고서에 허용되지 않은 **원본 개인정보가 포함되지 않는다.**

관련 계약: [C-04A](../C-04A-evidence-query.md) · [공통 필드](../common-fields.md) 의 `tenantId`

## T-08. 직원 판정·고객사 조치 — P3

**실행**
1. 직원이 증거를 선택해 판정을 저장한다.
2. 고객사에 대응 권고를 보낸다.
3. 고객사가 요청을 확인하고 **직접 처리한 결과**를 등록한다.
4. 같은 처리 명령을 재전송한다.

**기대 결과**
- 판정 revision 과 관련 근거가 기록된다.
- 고객사는 **자신에게 공개된** 조치 요청만 확인한다.
- **수동 등록 결과와 자동 실행 사실을 혼동하지 않는다.**
- 결과 이력이 중복 생성되지 않는다.

# 정산·현금흐름

## T-09. 취소·환불과 예상 정산 — P1 · P5

**실행**
1. 테스트 결제 성공 이벤트로 예상 정산을 만든다.
2. **확정된** 전액/부분 취소를 실제 지원하는 형태로 수신한다.
3. 같은 경제적 취소 이벤트를 재전송한다.
4. 취소 요청만 있고 **확정되지 않은** 이벤트를 입력한다.

**기대 결과**
- **확정된 금액만** 예상 정산에서 차감한다.
- 같은 취소·환불 금액이 두 번 차감되지 않는다.
- 당시 정책·계산 버전이 보존된다.
- 부분 취소 지원 범위는 CakeShop 원천 기능과 합의한 범위에 한정한다.

## T-10. Mock 입금·기초 대사 — P5

**실행**
1. 예상 정산과 **같은** Mock 금액을 등록한다.
2. **다른** 금액으로 등록해 차액을 확인한다.
3. 예상 정산 revision 이 갱신된 뒤 다시 비교한다.

**기대 결과**
- 일치 · 차이 · 미등록 상태와 비교 근거가 구분된다.
- **Mock 입금과 실제 은행 입금을 혼동하지 않는다.**
- 최신 정산 버전 기준으로 대사 결과를 확인할 수 있다.

## T-11. 현금흐름 독립 실행 — P6

**실행**
1. 결제·보안 이벤트 **없이** 시작 잔액과 예정 지출만 입력한다.
2. P5 예상 유입 반영을 켜고 끈다.
3. 예정 지출 금액·날짜를 수정하거나 삭제한다.

**기대 결과**
- **P5 데이터가 없어도** 날짜별 예상 잔액과 부족 경고가 계산된다.
- 선택한 P5 예상 순정산액만 반영된다.
- 입력값을 바꾸면 예상 잔액·부족 경고가 일관되게 갱신된다.

관련 계약: [C-07](../C-07-expected-settlement-query.md)

## T-12. 정산 조회 실패와 이중 계산 방지 — P5 · P6

**실행**
1. **정상 유입 0 원** / **데이터 없음** / **조회 실패** 상황을 각각 만든다.
2. 가상 수수료·취소를 **이미 반영한** 예상 순정산액을 P6 에 전달한다.
3. Mock 입금 정보도 함께 전달한다.

**기대 결과**
- **정상 0 원 · 자료 없음 · 조회 실패를 각각 다르게 표시한다.**
- P6 가 수수료·취소를 **다시 차감하지 않는다.**
- Mock 입금을 예상 정산액에 중복으로 더하지 않는다.

관련 계약: [C-07](../C-07-expected-settlement-query.md) — `resultStatus` 세 상태가 이것 때문에 있다

# 화면·배포 회귀

## T-13. HTTP 요청·응답과 권한 — P1 ~ P6

**실행**
1. 계약별 정상 요청을 보내고 응답 데이터·상태를 확인한다.
2. 필수값 누락, 잘못된 타입, 미인증, 역할 불일치, **다른 고객사 ID** 로 요청한다.
3. 생성·수정 명령을 같은 키로 재전송한다.

**기대 결과**
- 명세한 Request 와 Response 형식이 일치한다.
- **인증·권한 오류 / 유효성 오류 / 상태 충돌을 구분한다.**
- 중복 명령이 불필요한 새 결과를 만들지 않는다.

**응답 규칙** — 개별 API 에 필요한 상태만 실제 계약에 채택한다.

| 코드 | 뜻 |
|---|---|
| 200 / 201 / 202 / 204 | 조회·수정 / 생성 / **비동기 접수** / 삭제 |
| 400 / 401 / 403 / 404 / 409 | 잘못된 요청 / 미인증 / 권한 없음 / 조회 불가 / **상태·중복 충돌** |

오류에는 오류 코드와 요청 추적 ID 를 준다.
**상세 내부 오류 · 다른 고객사 데이터 · 비밀키는 반환하지 않는다.**

## T-14. 기존 CakeShop 정상 동작 — P1 · P2 · P5

**실행**
1. 신규 플랫폼 또는 FastAPI 를 **중단한다.**
2. CakeShop 의 기존 로그인·주문·결제·취소 기능을 실행한다.

**기대 결과**
- CakeShop 의 기존 핵심 거래 흐름이 **신규 플랫폼 응답을 기다리며 차단되지 않는다.**
- 실패한 이벤트 전달은 복구 정책에 따라 재전송할 수 있다.

> 이것이 [C-01](../C-01-cakeshop-event.md) 에서 **기록과 전송을 분리**한 이유다.
> 로그인 리스너는 INSERT 만 하고, HTTP 전송은 별도 작업이 맡는다.

## T-15. Spring Modulith·스키마 변경 회귀 — 전원

**실행**
1. 업무 모듈 검증과 ArchUnit 구조 검증을 실행한다.
2. FK · UNIQUE · 실제 DB 트랜잭션 테스트를 실행한다.
3. 원천 이벤트와 이벤트 발행 기록이 **한 트랜잭션**으로 저장되는지 확인한다.
4. 미완료 Registry 기록의 조회·복구·완료 처리를 시험한다.
5. **공유 필드의 타입이나 금액 의미를 바꾸면** 관련 소비자 계약 테스트를 다시 돌린다.
6. Flyway 로 **빈 DB 에 전체 마이그레이션**을 적용하고, 기존 버전 DB 에는 신규 변경만 적용한다.
7. 적용 이력 · 체크섬 · Registry 기술 테이블 생성과 **DDL 실패 후 복구**를 확인한다.

**기대 결과**
- 다른 모듈의 내부 Repository · Entity 를 우회 참조하지 않는다.
- DB 의 고객사 격리 · 중복 방지 · 동시성 제약이 실제로 동작한다.
- 서버 중단·재시작 후에도 미처리 이벤트를 잃지 않고 재처리할 수 있다.
- 다른 담당자에게 영향을 주는 변경은 **계약과 테스트에 함께** 반영된다.
- Flyway 가 빈 DB · 기존 DB 업그레이드에서 모두 성공하며 **이력과 실제 스키마가 일치**한다.
- Registry 기술 테이블은 업무 테이블과 **별도로** 검증한다.

> 1 번과 2 번의 일부는 이미 저장소에 있다 — `ModularityTests`(모듈 경계),
> `FlowSeparationTests`(보안·자금 흐름 분리). 5 번은 [공통 필드](../common-fields.md) 와
> 짝이다.
