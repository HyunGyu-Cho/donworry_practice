# PLANS.md — 작업 계획과 세션 복구

작업 계획서(Execution Plan)를 **어디에 · 무엇을 · 언제까지** 쓰는지 정한다.
계획서의 내용 자체는 각자 쓴다.

## 1. Plan 은 승인받는 문서가 아니다

**본인이 쓰고 본인이 바로 시작한다. 승인 절차는 없다.**
업무가 겹치지 않게 나눠 뒀고, 경계를 어기면 `ModularityTests` 가 막는다.
앞에 승인 단계를 또 두면 같은 일을 두 번 하게 된다.

그런데도 쓰는 이유는 하나다 — **코딩 에이전트에게 범위를 알려주기 위해서다.**
범위를 주지 않으면 시키지 않은 파일까지 고쳐 놔서 검토가 불가능해진다.

**예외는 하나뿐이다.** 공개 계약(C-01~C-07)을 바꾸는 작업은 상대 담당자의 확인을 받는다.
혼자 정할 수 없는 일이다. 나머지 멈춤 조건은 [AGENTS.md](../AGENTS.md#멈추고-사람에게-물어야-할-때) 에 있다.

## 2. Plan 이 필요한 작업 · 필요 없는 작업

| | 예 |
|---|---|
| **쓴다** | 새 기능, 테이블 추가, 이벤트·API 신설, 다른 모듈과 닿는 변경, 되돌리기 어려운 변경 |
| **안 쓴다** | 오탈자, 문구 수정, 주석, 테스트 1개 추가, 이미 Plan 에 적힌 단계의 실행 |

애매하면 쓴다. 다섯 줄짜리 Plan 도 Plan 이다.

## 3. 파일 이름과 위치

```
docs/exec-plans/
├── TEMPLATE.md          # 복사해서 시작한다
├── active/              # 지금 하고 있는 것
│   └── P2-RISK-01.md
└── completed/           # PR 병합·검증까지 끝난 것
```

파일 이름은 **Plan ID 그대로**다. Plan ID 는 `P<담당 번호>-<모듈>-<연번>` 이다.

| Plan ID | 내용 예시 |
|---|---|
| `P1-INTEGRATION-01` | CakeShop 이벤트 수신·중복 방지 |
| `P2-RISK-01` | 위험 규칙 실행·Alert 생성 |
| `P3-CASE-01` | Alert 기반 Case 생성 |
| `P4-JOB-01` | FastAPI Job 접수 |
| `P5-PROJECTION-01` | 확정 거래 반영 |
| `P6-FORECAST-01` | 독립 현금흐름 계산 |

P 번호가 누구인지는 [ROADMAP.md](ROADMAP.md) 에 있다.

**한 사람당 하나가 아니라, 한 번에 검토할 수 있는 기능 하나당 하나다.**
너무 커서 한눈에 안 들어오면 `-02`, `-03` 으로 쪼갠다.

## 4. 상태는 다섯 가지

| 상태 | 뜻 |
|---|---|
| `TODO` | 계획만 썼다 |
| `IN_PROGRESS` | 실제로 하고 있다 |
| `BLOCKED` | Mock 으로도 진행할 수 없다. **무엇 때문인지 적는다** |
| `REVIEW` | 구현·검증을 마치고 사람 확인을 기다린다 |
| `DONE` | 테스트·리뷰·병합까지 끝났다 |

> **코드를 다 썼다는 것은 `DONE` 이 아니다.** 에이전트가 "완료했습니다" 라고 답한 것도 아니다.
> PR 이 병합되고 실행 결과가 Plan 에 적혀 있어야 `DONE` 이다.

## 5. Plan 에 들어갈 것

[TEMPLATE.md](exec-plans/TEMPLATE.md) 를 복사해서 쓴다. 빈칸을 남겨 두지 않는다 —
해당 없으면 "없음" 이라고 적는다. 빈칸은 안 쓴 것인지 없는 것인지 구분되지 않는다.

## 6. Checkpoint — 세션이 끊길 때

에이전트와의 대화는 끊긴다. **다음 세션은 이전 대화를 기억하지 못한다.**
그래서 진행 상태를 Plan 파일에 남긴다. 기억이 아니라 Git 에서 이어 간다.

세션을 닫기 전에 Plan 의 Checkpoint 절에 적는다.

- 지금 상태와 브랜치·마지막 커밋
- 끝낸 단계 · 하다 만 단계
- **실제로 실행한 명령과 그 결과** (통과·실패 모두)
- 실패했다면 재현 방법
- 다른 담당자에게 물어야 할 것
- **바로 다음에 할 행동 한 가지**

새 세션은 이 순서로 읽는다.

1. [AGENTS.md](../AGENTS.md) → [ARCHITECTURE.md](../ARCHITECTURE.md)
2. `docs/exec-plans/active/` 의 자기 Plan 과 마지막 Checkpoint
3. `git status` · `git log` · `git diff` 로 **실제 코드**
4. 마지막 테스트 결과를 다시 돌려 본다

**Plan 과 코드가 다르면 코드가 기준이다.** 먼저 보고하고, 맞춘 뒤에 이어 간다.
커밋하지 않은 수정이 남아 있으면 완료가 아니다.

## 7. `completed/` 로 옮기는 때

세 가지가 모두 끝났을 때다.

- PR 이 병합됐다
- 실행한 검사와 **실제 결과**가 Plan 에 적혀 있다
- [ROADMAP.md](ROADMAP.md) 의 줄을 갱신했다

## 8. 하지 않는 것

- **실행하지 않은 테스트를 통과라고 적지 않는다.** 안 돌렸으면 "미실행" 이다
- 계약·설계 본문을 Plan 에 복사하지 않는다. `contracts/` 가 정본이고 Plan 은 링크만 건다
- 막힌 것을 숨기지 않는다. `BLOCKED` 는 잘못이 아니라 정보다
